# 需求—条件—策略—验证台账

更新日期：2026-11-12（Asia/Shanghai）。这里记录策略依据，测试执行结果见根目录 VALIDATION.md；新条件出现时更新本表，不能用旧测试结论证明新范围。

## 策略迭代记录

1. **初始**：定位项目及三个版本，以可运行的本地1.4.1后台执行结构为起点，保留旧目录。
2. **版本条件变化**：发现GitHub `3b3b071` 虽标为1.2.0，包含较新的判据、密钥和MAP修复。版本号不能代替代码审查，因此按能力比较吸纳。
3. **目标收敛**：用户明确优先当前浏览器的 ikanbot。将当前线路识别与AES-128 HLS完整性作为首要验收，不扩展为所有网站兼容承诺。
4. **并发风险发现**：安装版的64路/截断策略不具备完整性依据。改为有界请求与完整清单，新增资源上限、乱序/重试/缓存验证。
5. **恢复风险发现**：仅session任务元数据无法跨浏览器重启；仅jobId无法区分重试。增加local持久化、runId与revision，补跨会话与迟到事件测试。
6. **真实采样与安装**：目标站清单576片、53分21秒；4个位置的密文资源可解密为TS。Chrome 已重载2.0.0，实际弹窗识别第1集当前线路，并区分未播放状态。此证据覆盖解析、抽样和来源识别，不替代整段Chrome下载验收。
7. **交叉审查**：修复重试与新任务同时争用同一URL导致重复提交，以及保存确认期间取消后仍可能创建Chrome下载的竞态。新增回归后全套169项通过。文档同时明确当前背压在按序写入后推进窗口，同页换源可能保留旧候选。
8. **验收条件变化**：浏览器安全策略拒绝自动打开扩展内部URL；没有绕过限制。完整下载与播放器验收改由用户在当前真实页面操作，结果确认前保持“待验证”。
9. **用户试用反馈（2.0.1）**：补回预计剩余时间，移除设置键/弹窗，将保存位置与每次询问直接放在主页并自动保存；并发统一自动调节。用户说的“后台”指操作入口层级，不是要求移除Chrome内部持续下载执行器，因此保留下载任务与弹窗分离。
10. **真实保存的新证据**：用户实验产生699198696字节TS数据，但Chrome保存后缀为.txt。发现并修复OPFS输出MIME缺失，增加TS/MP4×OPFS/内存回归。用户明确不要这段视频，已删除文件和Chrome下载记录，不再重下；后续用短样本验证后缀，不能用文件头代替完整播放验收。
11. **操作简化后的新边界**：自动保存必须覆盖“快速编辑后关闭弹窗”。改为每次输入即发送、worker串行写，补齐迟到响应/关闭/失败后继续等回归；最新完整验证为185项通过。
12. **环境探测（2.1.0）**：用户指出旧实现仅依靠完成片吞吐、低起点和固定冷却，缺少直接环境观测。拆分环境控制器、请求调度器和字节预留，采集正文到达与写入事实；未知Content-Length不再强制逐片串行。
13. **采样与因果条件修正**：用户指出调节后的速度可能受系统延迟影响，不能直接推出并发收益。取消“无增益就回退”，增加请求代次、生效和稳定窗口；等待/样本不足单独解释。限流按实际请求代次处理，不因一批旧429反复砍目标。
14. **高并发条件修正**：用户提供固定64路约300MB/分钟的实测，并要求支持更多。64成为启动目标，256为工程保护上限；对照加入64/128/256，不能只用固定2路当易胜基线。实际目标受当前资源与服务器反馈约束。
15. **独立评估发现**：早期版本在限流和小预算场景明显慢于固定2路，已保留原报告。定位单次503误降、在途buffer重复扣除目标、memory cap解除后错误冷却，并修正。最终结论必须使用最新核心hash的新报告，不能沿用前版提速数字。
16. **最终简化决定（覆盖12–15的自动调节策略）**：用户认为过度复杂，明确只要主界面一个1–375滑条、默认64、持久保存，“压根不用算”。已删除自动控制器及其运行时接线，改为固定任务槽；保留被动速率、ETA、按序输出、缓存、重试与字节背压。新下载/重试使用最新偏好，运行中任务保持启动快照。自动算法试验只保留在工作目录历史记录，不作为本版功能或性能结论。

17. **视觉统一（2.1.1）**：用户要求粉紫配色、可爱动漫和统一2.5D羊，装饰不得妨碍点击。使用单一透明PNG贯穿顶部、空状态和扩展图标，轻量星星/泡泡只占标题留白；保留420×600尺寸、1–375滑条与现有主界面功能。验证改为图像加载、文字/焦点对比度、装饰指针穿透、四种界面状态和已有212项回归；不重新声称下载提速。

18. **任务页收敛（2.1.2）**：按用户要求把并发与保存位置放入下载任务页；移除子文件夹和每次询问，所有保存调用只使用文件名及saveAs:false，历史字段不再影响输出。增加终态任务删除，保留活动任务取消和缓存清理失败重试。验证新增默认目录约束、清理/持久化失败、重试/保存竞态、迟到消息及重开恢复，不以仅隐藏控件代替后台约束。

19. **来源页精简（2.1.3）**：按用户要求删除当前网页栏/网页名称播报、当前网页画面与搜索，重新读取视频来源改为右上角大号文字按钮。同步移除内容脚本自动/手动截图、后台图片缓存与消息，保留下载文件命名和播放器frame导航隔离。截图不再作为后续默认功能；验证转为刷新交互、无图片采集与旧缓存清理、来源发现、布局和任务回归。

20. **角色与动画（2.1.4）**：用户提供黑白长发、羊角的动漫角色，要求替换IP并为进度条加同类动画。统一一个本地透明角色PNG，替换旧小羊；以CSS轻量浮动/星光表现下载活动，位移仍由真实进度驱动。动画与下载调度完全分离；不因动画改变速度、ETA或并发。验收加入图像加载、角色边界、动画暂停/减少动态效果及既有任务回归。

21. **来源说明移除（2.1.5）**：用户要求删除“为什么发现它”。删除来源卡片的展开入口、证据与路径展示、专属样式和纯展示函数；后台识别判据继续用于判断媒体类型，任务说明不变。验证来源卡片精简及现有下载操作。

22. **全局实时并发（2.2.0）**：用户要求滑条直接控制所有下载任务，并在两端标注“稳 / 急”。手动1–375范围与默认64不变；升级为版本化广播，所有正在执行及排队的HLS任务同步最新值。升高立即增补任务槽，降低让在途分片完成，不重下已完成内容。保持一个HLS任务执行、其余排队与Chrome直链独立管理。验证指标改为实际分片准入、降档不取消、写盘顺序、快速变化最后值、旧消息隔离、持久化恢复与下发失败可重试；不将速度提升或设定值等于TCP连接数作为承诺。

23. **冷启动重新识别（2.2.1）**：用户反馈有时只有刷新网页才能识别，并要求检查并行/串行依赖。已确认旧刷新仅getMedia读缓存，页面去重在发送前生效，且popup来源初始化等待任务/偏好加载。新增可信popup触发的refreshMedia，扫描在状态队列外执行，报告ACK和最终快照按依赖等待；来源、任务和偏好三路并行，异步默认页签不覆盖用户选择。重新注入复用单实例、失败可补报、普通轮询只读。验证冷缓存、ACK等待、重复刷新、导航失效、框架受限、超时可重试及真实已打开页面不刷新恢复；不以添加固定延迟或持续保活掩盖时序。

## 后续遇到变化时怎么更新

先记录新的可重现条件（站点结构/失败阶段/错误/样本），关联上述需求；再调整策略与对应指标；新增能先复现后修复的回归；运行受影响测试和完整验证；记录哪些是真实网络/浏览器证据、哪些是模拟。不能仅修改文案使失败看起来成功。

待独立设计的范围：按站点权限迁移、直播录制、独立音视频轨混流、浏览器完全退出后自动续传、超大单分片流式落盘。它们不隐藏在本版“已完成”声明中。
