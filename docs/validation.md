## 已复现并修正的主要行为

- 撤回候选版错误的固定 5 片批次，改为根据实测实际并发数与总吞吐趋势计算目标、连续补位；写盘缓冲背压独立于并发优化，详见[自适应并发说明](adaptive-download.md)。
- 保存框取消后仍下载；磁盘写入失败后重复计数到超过 100%，页面无法重新开始。
- worker 恢复前捕获的新媒体被旧快照覆盖；恢复前关闭的标签页被旧快照恢复。
- 保存的截图只有 180 像素宽；换源后留旧图；同秒抓拍返回成功但缓存不更新。
- 无明确播放器目标的 iframe 广播响应竞态。
- 独立审查进一步发现：选中 A 的截图失败后会继续取 B 的原图。现已限制明确直链来源的匹配集合，内容脚本再次核对当前片源；新增对应回归。
- 独立音轨被忽略但仍报告完整成功。现已提示未合并音轨并保留单独清单出口，没有实现混流。
- 控制台没有逐条返回 CDP 结果。现已验证并发逆序回包匹配、超时、原生错误、断连和重连、鉴权及 CLI 退出码。

## 基本能力复查

本轮进一步检查“输入关系是否保留、判断是否仍有可用路径”，见[基本能力复查说明](capability-review.md)。修复包括：

| 能力 | 已复现的问题 | 验证的行为 |
|---|---|---|
| 媒体类型 | 无后缀 HLS 被早期 MP4 猜测锁定；线路提示又会把明确 MP4/WebM/FLV 改成 HLS | 调换 DOM 与响应头顺序后结果一致；真实 MIME 修正弱推测，明确后缀优先于弱线路提示；popup 实际下载入口随类型变化 |
| 分片识别 | `part`、`chunk`、`hls` 路径词使有效 MP4 消失 | 路径线索不单独隐藏明确媒体；TS/m4s 记录保留身份，后续直接播放证据可重新显示，避免重复计数 |
| 抓拍与原图 | 没有下载地址就没有入口；相关播放器失败后误取无关视频 | 无下载 URL 的 blob/srcObject 播放器可选择、抓拍、预览和保存原图；多个同源候选逐个可选；所选目标失败不换视频 |
| 来源与状态 | srcObject 更换但 URL 一直为空时旧图仍存在；缓存满后播放状态不再更新 | 比较 srcObject 对象身份并清理旧图；srcObject 优先于遗留 src 属性；播放状态报告独立于截图缓存数量 |
| 页面重载 | 同 URL 刷新只有 `loading` 状态而没有新 URL 字段时，旧媒体和图片未清理 | 清理旧文档状态；worker 恢复未完成时也不会复活旧记录，重载后到达的新媒体保留 |
| HLS 密钥 | 一个未知 KEYFORMAT 会挡住同段已有的可用 identity 密钥 | 两种标签顺序均得到正确 AES-128 解密字节；仅未知格式仍明确报错，不输出密文冒充视频 |
| HLS 初始化段 | 同 URI 不同范围/IV 被当成同一个初始化段；沿用后来的正文密钥；见 MAP 就改成 MP4 | 输出正确范围与解密内容；切回已缓存 MAP 仍重新写入正确初始化字节；TS 与 fMP4 根据已有容器证据区分 |
| 清单地址与候选 | 相对地址按重定向前位置解析；最高档失败即停止；登录 HTML 被当成分片清单 | 以最终清单地址解析媒体、音轨、密钥和 MAP；有效最高档直接使用，准备失败后尝试低档并保留原因；无效根清单明确报错，原始地址仍可复制 |
| 浏览器目标 | 非法目标偷偷使用旧目标；选择准备失败也改变活动目标；前进后退跨页发送 | 只有省略目标可使用已确认目标；准备成功后提交；失败保留旧画面；候选首帧暂存；多步历史动作始终发往原目标 |
| CLI 结果 | 字符串 `"false"`、数字 `1` 或 HTTP 错误被当成功 | 严格要求布尔 `ok` 和 2xx；保留结构化错误及 CDP 原始结果，包括脚本异常详情 |

独立审查使用另外构造的 VM/HTTP/WS 场景复验媒体证据顺序、文档复用、多个播放器选择以及多个查看器的目标事务。审查发现的“弱线路提示覆盖明确文件后缀”和“HTML 冒充 HLS”均先复现再修复；后者通过实际下载处理器写出预期的高档/低档字节，并检查写入关闭及 UI 选择原因。

HLS 档位回退只覆盖清单、密钥、初始化段等下载计划的准备失败，不在下载中途混合不同档位。清单递归采用当前引用链的循环检测；已验证 20 层非循环嵌套仍可解析，没有用固定层数禁止这类清单。

自适应并发测试验证了实际集成路径：在任何媒体片都没有完成时，原始 downloader 已根据收到的 chunks 把模拟实际请求数从 1 上探到 5 以上；禁止用 `arrayBuffer()` 读取这些长流，以检查测速确实发生在下载过程中。背压、尾段、明显欠载和断流窗口不进入拟合，也不能与之前未收齐的样本拼成一组。

独立审查复现并修正了两类趋势误判：组内零散布而组间仅 0.1% 抖动会反复重启上探；平滑接近速度上限时，微小正斜率会导致并发长期增长。加入相对收益容差、固定锚点漂移判断及近邻坐标保留后，两项确定性回归通过。构造的尖峰函数在后 120 窗平均达到峰值的约 93.52%；构造的渐近平台在后 120 窗运行于 22～24 并发，平均达到函数速度上限的约 94.35%。这些数值是合成函数验收结果，不是实际网站性能数据。

## 尚未完成的实测

启动本环境中的 Chromium 已尝试，浏览器在创建单例锁时失败：`socket() failed: Operation not permitted`。这不妨碍本地 TCP 的 HTTP/WS 集成测试，但阻止了本轮浏览器本体验证。

尚未验证：真实 Chrome 加载扩展、真实视频画面保存与下载后播放、自适应并发在用户实际网站上的吞吐表现及登录态/请求头要求、Windows 批处理启动、控制台画面点击位置和中文输入法。

srcObject 对象替换、URL 变化和文档变化已有回归。同一个 MediaSource/blob 地址或同一个 MediaStream 对象若只更换内部内容且没有相应换源事件，仍无法保证识别。blob/HLS 卡片的截图仅标为当前播放器画面，不应当作某条清单身份已被证实。原图留在页面内存，刷新、换源或截图缓存淘汰后需要重新抓拍。

本轮未改变特殊 frame 的内容脚本注入配置；about:blank、srcdoc、blob **文档**内播放器尚未做注入和抓拍验收。这与已覆盖的普通文档内 blob **媒体 URL** 是不同场景。

HLS 仍使用浏览器内分片合并，尚未支持独立音视频混流、所有 DRM/加密格式、所有不连续流和动态直播清单。fMP4/MAP/Range 与 AES 的已列测试只覆盖明确构造的用例，不代表完整协议覆盖。

## 本机验收建议

1. 在新版本扩展上刷新一个原本可用的网页，确认媒体发现和下载保持正常。
2. 对同一页面切集、同秒抓拍、iframe 播放器分别取图，检查保存图片尺寸与来源。
   对只有 blob/srcObject 播放器而没有下载地址的页面，检查播放器卡片；多个播放器并存时逐个选择，核对原图来源。同地址刷新后检查旧媒体与旧图是否清理。
3. 取消保存框、下载中取消，再次开始，确认页面可恢复。
   对足够长的下载观察总速度与实际/目标并发；保存文件仍须保持媒体片顺序，写盘变慢时不应把缓冲停顿误当成网络趋势。
4. 对一个已知带独立音轨的清单确认提示；对普通清单检查下载文件画面、声音及长度。
   对存在多个画质的清单确认实际选择；若高档准备失败，检查低档及失败原因。使用重定向、范围或加密初始化段时，仍需核验最终文件播放。
5. 启动控制器，依次运行 health、tabs、读取标题和截图，再核对实际页面结果。
   切换到不能准备画面的目标，检查原标签仍可操作；前进/后退等待期间切换标签，检查历史动作仍落在发起操作的页。

这份候选改动应在完成上述真实浏览器验收后再作为稳定版合并。
