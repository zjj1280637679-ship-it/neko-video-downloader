# 分片并发：根据总吞吐量趋势计算目标

本轮纠正了候选版中“固定 5 片一批、整批写完再继续”的改动。目标是根据上探过程中实测的分片并发数量和总下载速度，计算合适的并发量。成功/失败计数、重试次数和缓冲大小都不是并发优化函数的输入。

## 控制器的两个测量输入

`ThroughputController.observe({ concurrency, bytesPerSecond })` 只接收实际并发数和总接收速度。所有状态由这两项的有效历史推导；返回整数目标并发 `targetConcurrency`。

- **实际并发 N**：在同一测速窗口内，对正在等待 HTTP 响应或读取响应体的请求数量做时间加权平均。重试等待、解密和写盘不计为正在下载，因此 N 可以是小数。
- **总速度 V**：该窗口所有分片响应体实际收到的字节之和，除以窗口实际经过的时间。它既不是单片速度的平均值，也不是一个分片完成时才一次性加入它的全部大小。

默认窗口为 1 秒，使用 `performance.now()` 的实际时间差。读取 `Response.body.getReader()` 的每个 chunk 时立即记账，大分片尚未完成也能参与测速。服务器声明的 Content-Length 和清单中的媒体时长都不参与计算。

真实重试再次收到的字节属于真实接收量，会在到达时计一次；重试不会重新加入此前已计过的字节。已完成进度和输出文件大小则只在某片最终成功时增加一次，分别表示网络吞吐和有效输出。

## 函数如何决定下一档

每个目标档位收集 3 个有效窗口，以总速度中位数减少单个异常窗口的影响，并用中位绝对偏差估计测量散布。响应点同时保留真实 N 与发出请求时的整数目标，避免把目标数冒充实际请求数。

比较速度时，使用当前网络阶段最佳实测总速度的 3% 加上测量散布作为收益容差，避免趋近带宽上限后仍因极小的正斜率无限上探。候选档位始终与这个阶段的最佳值比较，不逐档累积退让。网络漂移则与固定锚点比较，采用 6% 加测量散布的独立门槛，防止 0.1% 抖动被误认成网络条件改变。

冷启动从 1 开始；取得第一个响应点后探测 2，以得到计算趋势所需的两个档位。之后，在实测总速度有显著增长的区间，计算局部弹性：

$$
e=\frac{\ln(V_2/V_1)}{\ln(N_2/N_1)}
$$

下一档目标为：

$$
T_{next}=\left\lceil T_2\,2^{\operatorname{clamp}(e,0,1)}\right\rceil
$$

其中 N 是实际并发，T 是整数目标。若实际 N 没有形成可分离的两个坐标，会先探测一个更宽的比例区间。

| 实测关系 | 控制行为 |
|---|---|
| 并发翻倍，总速度也近似翻倍 | 弹性接近 1，可继续倍增探测，例如 1、2、4、8、16 |
| 并发增加，总速度仍增长但收益变小 | 弹性处于 0 与 1 之间，自动缩小上探比例 |
| 总速度持平或下降 | 利用已测响应点包围较好区域，测试相邻未测区间的中点 |
| 已测相邻整数档位限定局部峰值或平台 | 采用较好的实测档位；差异在收益容差与测量散布范围内时优先较小的并发 |
| 稳定运行后仍有增长空间 | 周期性复测相邻响应点，缺少邻点时进行比例探测，再依据新实测曲线调整 |
| 同一档位的总速度明显变化 | 丢弃旧网络条件下的比较依据，重建当前响应曲线 |

这里没有“每完成一片加 1”“失败一次减 1”的控制规则。函数结果需要取整数，某次探测恰好与上一档相差 1 是离散分辨率，不是固定加减的调节器。

普通周期探测保留已有曲线和邻档坐标。确认网络条件改变时，旧速度退出新阶段的比较，但仍可复用已测过的并发坐标安排近邻探测，减少重复大幅上探。

实现没有生产并发上限常量。调度器最多只能发出尚未完成的任务数量；JavaScript 安全整数范围仅是数值表示边界。

## 连续补位与有序保存

`runAdaptiveDownload()` 按当前计算出的目标持续安排请求。一片完成就可以补位，不等待其他片完成或某批写完。目标降低时不丢弃已有请求，等待实际占用自然下降到新目标。

返回顺序和保存顺序分离：后返回的较早分片仍排在正确位置写入，fMP4 初始化段仍在对应媒体片之前写入。失败片按现有规则报告并跳过；写盘错误不会触发分片重下或重复计算完成进度。

字节缓冲使用默认 64 MiB 水位。达到水位时暂停新增请求和后续片的进一步读取，最早尚未写入的片仍允许完成，避免乱序等待形成死锁。释放已写入数据后恢复执行。**缓冲水位不修改目标并发。**

这个水位是背压阈值，不是浏览器总内存的硬上限：已经提交的读取、最早片的剩余数据、解密及合并数组的临时副本可能使占用超过水位。无法直接写盘时，Blob 合并仍会保存完整输出，整个视频的内存不会受这个队列水位限制。

## 无效测速窗口

以下窗口只展示测量，不进入并发控制历史：

- 没有足够尚未发出的分片，已经进入尾段。
- 缓冲背压暂停了网络执行。
- 调档过渡导致实际占用不符合窗口目标。
- 实际平均占用低于目标的 90%，例如重试等待占了大量时间。
- 没收到字节，或者响应体只能一次性读取、无法观察字节到达时间。

跳过窗口时会清空尚未收齐的一组样本，避免把停顿前后的窗口拼成同一个稳定测量点。清空操作不改变并发目标。取消会停止整个调度器、终止在途请求并释放未提交的写入器。

## 已验证与未验证

自动化测试覆盖线性增长越过 5 及常见固定阈值、平台、峰值下降、噪声、网络条件变化、浮点实际 N、连续补位、乱序写盘、尾段与背压排除、重试字节计量及取消/写盘失败。

还直接运行了原始 `downloader.js`，通过真正的 ReadableStream/Response 分段送入字节：在任何媒体片都未完成时，控制器已使真实模拟请求数增长到 5 以上。该测试禁止调用媒体响应的 `arrayBuffer()`，用来防止测速退回“整片完成后才计数”。

这是一种基于当前已探索区域的在线搜索，不保证任意未知响应函数的全局最优。短任务可能在收集足够窗口之前结束；网站限速、网络变化和片段内容差异仍可能影响判断。本轮尚未完成真实 Chrome 与用户站点的吞吐性能验收。
