## v1.4.0 总速度自适应与播放状态

- 自动并行只比较改变并行数前后的合计有效下载速度，不以单路平均速度或错误数量决定增减。重试和退避时间留在实际测量窗口内。
- 定向测试覆盖：单路下降但总速提升仍增加、总速仅提升 5% 也可保留增加、固定总速撤回无收益探测、持续总速下降尝试减少、减少后降速则恢复、429/超时不直接改并行、缓存与尾段不误导学习、有序输出和 1–8 路上限。
- 采用本地真实 HTTP 分片传输与受控带宽模型、实际服务器计时、生产默认 4 秒测量窗口。两种模型都完成 512 / 512 片，共 6,160,384 字节；输出 SHA-256 均为 `07e14f794a341504ceb6d860c6978a25b323f058a370670b210dc355f6e52e13`。
- 单路随并行增加而变慢、总速先上升再封顶的模型：2 → 3 路后保留；3 → 4 路未提速，回退至 3 路，35.08 秒完成。
- 固定服务器总带宽模型：2 → 3 路后实际有效吞吐有小幅收益，保留 3 路；两次 3 → 4 路尝试均回退，43.01 秒完成。请求间隔和启动阶段会影响实际吞吐，不能宣称固定带宽下一定回到 2 路。
- 上述为受控本地网络实验，不代表目标网站的实测提速，也不保证所有网络条件下的全局最优并行数。
- 捕获测试区分真实播放、预加载、暂停后拖动、暂停保留记录、换源、刷新、嵌套框架、框架移除与 BFCache 恢复；旧文档消息不能重新污染状态。播放后 10 秒无来源结束持续识别提示，无法确认的 iframe 保持未知。

## v1.3.1 解密失败调查与修复

2026-11-11，用户确认 v1.3.0 重载后弹窗下载正常启动，但约 80% 时出现“第 498 个分片下载失败：AES-128 解密失败，请重新播放网页后获取最新线路”。

代码核对发现：原版已使用 5 片并行，网络请求有重试，但 AES 解密位于重试范围之外；任务失败时会清理已下载内容。故修复重点是完整资源重试与保留成功分片，并非简单增加并发。

- 原测试线路第 498 片重新获取三次，均为 HTTP 200、837,552 字节密文、16 字节密钥，并成功解密为 837,540 字节。三次散列相同。没有复现原先的服务器异常，因此不确定原事件是错误响应、损坏数据还是密钥问题。
- 使用真实线路第 496–500 片，测试代码刻意截断第 498 片的一字节密文；这属于受控故障注入，不是原故障复现。
- 第 498 片严格尝试 6 次后失败，另外 4 片保留；关闭注入后续传只请求第 498 片一次，5 / 5 片成功，输出 3,326,096 字节。
- 五片合并 SHA-256：`2f64c5775f15bd5b1695cfc31b6af74b5565c6bb9effb2d8cbef50f8f933c087`。
- 自动测试用真实 WebCrypto AES 验证同样场景，逐片请求次数从 `[1,6,1]` 变为 `[1,7,1]`，输出与原文逐字节一致，完成后自有分片缓存与合并临时文件清理，外部数据保留。
- 新增清单签名、分片 SHA-256 校验、同大小损坏/丢片补下、恢复时清单暂错、排队续传取消、缓存删除范围、并行参数及重试状态恢复测试。
- Chrome 的本地 HTTP 界面预览验证“继续下载”切换状态、设置并行数并重新打开确认保存，以及 420×600 布局。没有控制台 error/warn。截图中的失败片数是明确的模拟数据。

## 已安装 Chrome 扩展仍需验收

用户已重载 v1.3.1 并开始重新下载，截至本记录未收到保存完成及播放检查结果。v1.4.0 与本轮 v1.4.1 均单独打包，未覆盖原加载目录，以免重载中断当前任务。浏览器控制工具拒绝访问 `chrome://extensions/`（仅允许 HTTP/HTTPS），原生窗口控制也无法可靠确认浏览器地址；没有换通道绕过这些限制。

1. 当前任务结束后，将 v1.4.1 文件更新至原加载目录，再在 Chrome 扩展管理页点击“重新加载”，确认版本为 1.4.1。重载会丢失本次浏览器会话的续传条件，勿在未完成任务时重载。
2. 刷新目标视频页面并播放选中的测试内容，打开扩展，确认当前来源。
3. 在弹窗点击下载；关闭并重开弹窗查看进度。若有可恢复失败，保持浏览器运行，点击“继续下载”，确认复用缓存补缺失片。
4. 完成后点击“在文件夹中显示”，核对文件在 Chrome 默认目录，用支持 TS 的播放器检查画面、声音与跳转。

在上述真实安装验收完成前，不把本轮结果描述为已在用户安装的 Chrome 扩展中完成端到端闭环。
